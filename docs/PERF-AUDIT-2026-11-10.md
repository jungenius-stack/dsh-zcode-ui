## 1. 量纲与口径审计（M2）

本任务的核心风险就在口径上——同一个「样式成本」有多种测法，结论相差 1000 倍。

| 对象 | 原始口径 | 统一后口径 | 备注 |
| --- | --- | --- | --- |
| CSS 规则数 | 正则数 `{` | 浏览器 CSSOM `cssRules` | 正则把 URL/对象字面量算进去，565 个模板串里只有 30 个是真 CSS |
| 样式成本 | JS 计时 + `offsetHeight` | CDP `RecalcStyleDuration` 增量 | JS 计时会被布局读缓存污染，测出 0.000ms |
| 失效范围 | 切任意 class | 切**被规则依赖**的 class | 无依赖时 Blink 直接跳过重算，测出 0.000ms |
| 成本归属 | 「整类移除」 | 每档独立页面各测一次 | 运行中重写 `textContent` 会自触发完整重算，产生负值 |

## 2. 坑位清单（M8 分级后）


这次审计我先后得出过两个「重大发现」，都被后续实测推翻。过程比结论更值得留下来。

| 轮次 | 我当时的结论 | 实测结果 | 错因 |
| --- | --- | --- | --- |
| 1 | 「`virtual-skip` 的 observer 每次遍历 23000 节点，推流时拖慢」 | 0.0026ms/次 | Blink 缓存 `getElementsByTagName('*').length`，根本没遍历 |
| 2 | 「`:has()` 贵 640 倍，200 条要 146ms」 | 真实插件规则只有 16ms | 用了**病态用例** `body.dark :has(> .x0)`：选择器左侧无可索引的键，必须对每个元素求值 |

**教训（已回写候选）**：合成探针的「最坏情况」不等于「真实情况」。测量一个系统里已有的规则，必须**注入那批真实规则本身**，不能用结构相似的合成规则代替。

### ✅ 已查证到的事实

### 2.1 插件 CSS 的真实规模（浏览器 CSSOM 口径）

| 项 | 值 | 怎么查的 |
| --- | --- | --- |
| 模板串总数 | 565 | `perf-plugin-css-audit.mjs` |
| 真 CSS 样式块 | 30（其余 535 是 URL / 对象字面量） | 同上，由浏览器判定 |
| 规则总数 | **776** | 同上 |
| 普通类 | 660 | 同上 |
| `[class*=]` 属性子串 | 56 | 同上 |
| `:has()` | 47 | 同上 |
| 后代通配 | 13 | 同上 |

> 与文档现值对照：§40.3 记 535 条、§51.1 记 550 条。本次独立测得 776 条，**高出 40%**。差异可能来自计数口径（是否拆逗号、是否算 @media 内层），已记录，未判定哪方为准。

### 2.2 成本由「命中元素数」决定，不由选择器形态决定

真实规模 DOM（23042 节点，对齐 §50.1 的 23231），200 条规则，触发器被规则依赖：

| 规则形态 | 每次样式重算 |
| --- | --- |
| 0 条规则（基线） | 0.00 ms |
| 200 普通类，**不匹配** | 0.19 ms |
| 200 属性子串，**不匹配** | 0.39 ms |
| 200 `:has()`，**不匹配** | 15.97 ms |
| 200 根锚定 `:has()`，**不匹配** | 13.55 ms |
| 200 条**全局通配**（每条命中所有元素） | 107.37 ms |
| 200 条**实际命中的规则** | 138.55 ms |

三条可复核的推论：
1. **不匹配时几乎免费**（普通类 0.19ms），所以「规则多」本身不是问题；
2. **`:has()` 即使不匹配也要 16ms** —— 这是它独有的代价，因为必须求值才能知道不匹配；
3. **命中所有元素的通配是灾难**（107ms），但插件只有 1 条真全局通配（`html[data-document-hidden] *`），且只在页面隐藏时存在。

### 2.3 流式场景 vs 全树失效，差 1000 倍

| 场景 | 插件增量成本 |
| --- | --- |
| 推流追加一条消息（增量失效） | **0.026 ms/次** |
| 切根属性触发全树失效 | **26 ms/次** |

**用户报告的「推流时输入卡」落在第一栏。** 插件在这个场景里几乎不花钱。

### 2.4 25 个 MutationObserver 不是瓶颈

| 配置 | 同步耗时（200 次追加） |
| --- | --- |
| 0 个 observer | 0.20 ms |
| 25 个空回调 | 0.30 ms |
| 25 个真查询（含全子树计数） | 0.40 ms |

observer 回调按批合并执行（200 次追加只触发 25 次回调），且真查询与空回调只差 0.1ms。

### 2.5 ✅ 已修：`hasForeignFooterContent` 25 倍提速

| 实现 | 页脚 5200 元素 |
| --- | --- |
| 旧：`[...querySelectorAll('*')].some(...)` | 0.489 ms |
| 新：`for...of` 直接迭代 + 命中即返回 | **0.019 ms** |

**结果一致性已验证**（有外来内容 / 无外来内容两种页脚，新旧实现结论相同）。已在 `foreign-content-contract.ts:70` 落地，`tests/foreign-surface-observer.spec.ts` 6 条全过，门禁全绿。

**监控三问**：
- 谁看：下次活宿主性能录制时

### 大象 2：`data-dcu-scrollbar-autohide` 总开关挂在 `html` 上

## 6. 回写预告（M12，待确认后入 `cards/code.yaml`）

**CODE-051（候选）· 合成探针的「最坏情况」冒充真实情况**

- **描述**：用结构相似但参数极端的合成规则去代表系统里已有的规则，得出量化结论。最典型的表现是「实测某选择器慢 640 倍」，而真实系统里同一选择器只慢 1.2 倍。
- **触发词**：「合成测试」「探针」「合成 DOM」「代表真实」
- **为什么是坑**：它产出的数字**看起来比真实测量更可信**（有具体毫秒数、有倍增比），但分母是自设的。更糟的是它会导向真实但无效的优化。
- **本任务的两次实例**：
  1. 改 textarea 测打字 → 增量重算 → 0.01ms → 误读为「选择器不重要」；
  2. `body.dark :has(> .x0)` → 病态全量 → 146ms → 误读为「:has() 贵 640 倍」。
- **规避动作**：测一个已有系统时，**必须注入那批真实规则本身**，不能用结构相似的合成规则代替；测完必须做一次「换形态、同语义」的对照。
- **验证器**：把真实规则与其合成替代分别注入真实规模 DOM，数据差 >3× 即判定合成探针不可用。
- **严重度**：S=3 / O=4 / D=4

**CODE-052（候选）· 「触发器无效」导致的零成本假象**

- **描述**：测量样式重算成本时，切一个没有规则依赖的 class。Blink 判定「无匹配规则受影响」，直接跳过重算，测出 0.000ms，被误读成「这个特性不花钱」。
- **证据**：本任务中 `html.dark` 前缀的 200 条规则，切 `perf-t` 测得 0.000ms；改成切 `dark` 后测得 0.204ms。
- **规避动作**：全树失效的触发器**必须真的出现在被测规则里**；测完先跑一次「无规则基线」，基线不为 0 说明触发器有问题。
- **严重度**：S=2 / O=3 / D=5（隐蔽度极高：0ms 看起来像好消息）
