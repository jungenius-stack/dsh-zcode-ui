## 3. 唯一有明确参照的缺口：TA1

**ZCode 浅色侧栏 `oklch(97% 0 0)`，DSH 是 `#f0f0f0`。**

换算：`oklch(97%)` 的 Lab L=97 → sRGB 约 **`#f7f7f7`**（249）。
DSH 的 `#f0f0f0`（240）比它暗 **9 个灰阶**。

**为什么标「高影响」**：这不是孤立色值。G14 那轮我把侧栏 secondary/tertiary 的
alpha 从 0.6 抬到 0.85/0.75，**正是因为 `#f0f0f0` 比 ZCode 背景暗、同一 alpha 压不出对比度**。
底色改成 `#f7f7f7` 后，那两个 alpha 就**必须重算**，否则会过冲（变得比 ZCode 更实）。

→ 所以 TA1 不是「改一个色值」，而是**牵动 G14 三个令牌的连锁重标定**。建议单独排一轮做。

## 4. 审计方法说明（可复核）

1. 用 CDP 取六组件的 `backgroundColor` / `color`；
2. 双主题各跑一遍（切 `body[data-ds-dark-theme]` + `html[data-ds-theme-source]` + `colorScheme`）；
3. 用浏览器 canvas 把 `tokens.json` 的 231 个值（含 `oklch` / `#hex`）统一归一化为 `rgb()` 再比对
   —— **第一版用字符串匹配，浅色全判「未命中」，是方法错误**（`oklch(97% 0 0)` 与 `rgb(247,247,247)`
   字符串不等但语义相同）。改用 canvas 归一化后才得到上表。

## 4.5 TA1 实施结果（2026-10-27，已改并验证）

**改动**：`.dcu-root,.dcu-settings-page,.dcu-home` 的 `--dcu-sidebar-background`
`#f0f0f0` → **`#f7f7f7`**（通道 240 → 247）。

**取 #f7f7f7 的依据**：ZCode `--color-sidebar` 浅色 `oklch(97% 0 0)` = 通道 245（`#f5f5f5`），
`--color-background` 浅色 `oklch(98.5% 0 0)` = 通道 248（`#f8f8f8`），**取中值 247**。

### G14 联动核对结论：**alpha 不需要改**

| 指标 | 旧底 `#f0f0f0` | 新底 `#f7f7f7` | 变化 |
|---|---|---|---|
| secondary 85% 对比度 | 6.05:1 | **6.34:1** | **+0.29（上升）** |
| tertiary 75% 对比度 | 4.61:1 | **4.76:1** | **+0.15（上升）** |

**原因**：底色变亮 ⇒ 同 alpha 的合成色与底色的距离变大 ⇒ 对比度只升不降。
所以 `#404040 85% / 75%` **原值保持**，双双仍过 AA。

### 三档最终实测（活页面）

| 档 | 渲染色 | 对比度 | L* | ΔL* |
|---|---|---|---|---|
| primary | `rgb(38,38,38)` | **14.13:1** ✅ | 15.2 | — |
| secondary | `rgb(91,91,91)` | **6.34:1** ✅ | 38.7 | **ΔL*(pri-sec)=23.5** ✅ |
| tertiary | `rgb(110,110,110)` | **4.76:1** ✅ | 46.4 | **ΔL*(sec-ter)=7.8** ✅ |

**副作用**：深色未受影响（`rgb(22,22,22)` / `#161616` 实测确认）。

### 验证方法的重要修正

**第一版测量错了**：我用临时 `div` 去读 `color-mix(...)` 的 computed color，
拿到的是 **`rgb(38,38,38)`（三档全一样）** —— 因为 `color-mix` 在未渲染合成前
返回的是基色，不是合成结果。

**正确做法**：读**真实使用该令牌的元素**（`.dcu-wb-project-title` / `.dcu-wb-empty`），
拿到的是 `oklab(0.371493 … / 0.85)` 这种带 alpha 的形态，
再用 `255 × L³` 转 sRGB 并与底色合成，才是最终渲染色。

## 4.6 TA1 修正：分层取值（2026-10-27 第 19 轮）

**上一版取中值 #f7f7f7 是错的。** 评审方指出 ZCode 是**分层**的，并用 canvas 像素回读做了权威换算；
我用同样方法**独立复现**，两个已知值反验全部吻合：

```
oklch(97%   0 0) → rgb(245) = #f5f5f5   ← --color-sidebar     （侧栏层）
oklch(98.5% 0 0) → rgb(250) = #fafafa   ← --color-background  （内容画布层）
反验 oklch(87%   0 0) → rgb(212)  ← 正是深色前景 ✅
反验 oklch(37.1% 0 0) → rgb(64)   ← 正是 G14 基色 ✅
```

**我上轮把 98.5% 算成 248，实际是 250**（差 2 个通道）。

### 为什么不能取中值

**245 与 250 这 5 个通道的差本身就是设计语言**——侧栏略暗于内容画布，用于区分层级。
取中值 247 等于把两层压平：两侧都不准，还丢掉了层级差。

### 正确映射（已实施）

| 元素 | 取值 | 依据 |
|---|---|---|
| `.dcu-root`（插件侧栏壳） | **#f5f5f5 (245)** | ZCode `--color-sidebar` |
| `.dcu-settings-page` / `.dcu-home`（整页视图） | **#fafafa (250)** | ZCode `--color-background` |

**实施中踩到的坑**：`.dcu-settings-page` 的整页底色**不来自 `--dcu-sidebar-background`**
（那只驱动左侧导航栏 `--sp-nav`），而来自 `--sp-bg`。
第一版改错了变量，实测底色仍是 248；改 `--sp-bg` 才生效。
另外深色必须显式回落，否则会继承浅色的 `#fafafa` 变成亮底深色页。

### G14 在三代底色上的复算

| 底色 | secondary 85% | tertiary 75% | ΔL*(s-t) |
|---|---|---|---|
| `#f0f0f0`（240，旧·错） | 6.05:1 | 4.61:1 | 7.4 |
| `#f7f7f7`（247，上轮·中值） | 6.34:1 | 4.76:1 | 7.8 |
| **`#f5f5f5`（245，本轮·正确）** | **6.23:1** | **4.75:1** | **7.4** |

**三代底色上都过 AA**，故 G14 的 `85%/75%` 始终不需要改。

### 活页面验证（最终）

```
.dcu-root            rgb(245,245,245)  ✅ 目标 245±1
.dcu-settings-page   rgb(250,250,250)  ✅ 目标 250±1
深色未受影响           rgb(22,22,22)    ✅
副作用恢复             theme-zai-dark   ✅
```

## 4.7 第二个坑：深色回落的循环引用（2026-10-27 第 20 轮）

给设置页加深色回落时，我写成：
```css
/* 浅色块 */  --dsw-alias-bg-base: var(--dcu-settings-page-bg, #fafafa);
/* 深色块 */  --dcu-settings-page-bg: var(--dsw-alias-bg-base);   ← 互引
```
**两者互引形成循环 ⇒ 解析为空 ⇒ 深色设置页底色变 `rgba(0,0,0,0)`（透明）**。
实测表现：深色下设置页底色透明，会透出下层内容。

**修法**：深色块直接给具体值，不再回引：
```css
body[data-ds-dark-theme] .dcu-settings-page{
  --dcu-settings-page-bg:#161616;
  --dsw-alias-bg-base:#161616;
}
```
深色取 ZCode `--color-background` dark = `#161616`。

> 教训：**CSS 变量做「覆盖 + 回落」时，两个方向不能同时引用**。
> 一旦形成环，浏览器不报错、只是解析为空——比报错更难查。
