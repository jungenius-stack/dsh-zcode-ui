# 02 动效与滚动（Motion & Scrolling）

> 全部数值来自 ZCode 源码（bundle `Vst`/`ypn`/时间线组件）+ 双端 CDP 实测。实现前必读。

## 1. 基础过渡

| 项 | 值 | 来源 |
|---|---|---|
| 微交互动效（hover 波、浮层淡入） | `transition 150ms cubic-bezier(0, 0, 0.2, 1)` | 源码 `duration-150 ease-out` |
| 参与过渡的属性 | 刻度：`transform, opacity, background-color`（**三件缺一不可**——只过渡 transform+opacity 会让变色瞬跳，教训见报告一坑 2） | 实测 |
| 浮层出现 | `opacity, transform, visibility` 150ms ease-out；浮层内淡入 90ms（feedback 档） | 源码+实测 |
| 波的数值 | 距离 0/1/2/≥3 → scaleX 2.6/1.7/1.25/1，opacity 1/.86/.72/.58，d0 全前景色 | 源码 `Vst` |

## 2. 点击滚动（平滑跳转）

- **曲线是 Chrome 原生 smooth 的实测采样，不是 easeInOutCubic**（对称缓动起步偏慢后段偏快，主观「不顺」）。21 点归一化：
  ```
  [0, .011, .061, .204, .471, .652, .761, .834, .885, .923, .950, .970, .984, .993, .998, 1, 1]
  ```
  形态 = 非对称 ease-out：前 20% 时间走完 47%，后 40% 只走 1.6%。实现用查表+线性插值（误差 <0.005）。
- 时长按**距离**自适应，不是常量：本机实测每帧位移与帧耗强相关（100px→35ms/帧；1000px→60ms；3000px→88ms）。策略：保证平均每帧位移 400~800px（对应 41~60ms/帧可接受区间），设上下限（DSH 当前 320~2200ms、3.2px/ms，可按实测微调）。
- **reduced-motion 时点击必须瞬跳**（`behavior:'auto'`），这是 ZCode 明确语义（源码 `c?'auto':'smooth'`，c=prefersReducedMotion）。CSS 的 transition-none 不覆盖 JS 驱动的滚动动画，必须在 JS 入口分支。
- **禁止容器级 `scroll-behavior:smooth`**：宿主「跟随底部」每次流式 tick 赋值 scrollTop，会把赋值也动画化，永远追不上新消息。只在点击这一次调用 smooth/自绘动画，结束即释放。
- 点击拦截技巧（DSH 当前方案，已验证无闪跳）：capture 阶段监听宿主滚动写入 → 首次大幅位移时同步回滚起点 → 自绘动画到目标。双 rAF 回滚方案有 300~800ms 闪跳窗口（教训报告四坑 1），不要回退到它。

## 3. 性能预算（DSH 特有约束）

- ZCode 滚动区 ~737 节点（8ms/帧）；DSH 会话可达 38k+ 节点、滚动区 7 万 px。跨数万像素的 smooth 每帧都驱动虚拟列表重挂载 → 150~400ms/帧，肉眼只剩 4~5 步。
- **预算规则**：平均每帧位移控制在 400~800px；超长距离考虑「瞬移到目标前 0.6 屏 + 最后一段滑入」（未实施，实施前需验「跟随底部」互扰）。
- 点击后宿主写入 scrollTop 前有 ~0.5~1s 宿主内部延迟（跨像素挂载成本），期间应给点击条即时视觉反馈（待实施）。

## 4. reduced-motion 全集

| 路径 | ZCode 行为 | DSH 现状 |
|---|---|---|
| CSS 过渡（刻度/预览/侧栏） | `motion-reduce:transition-none` | ✅ 已做 |

## 5. 动效细节清单（易漏）

- 静息当前条的 .9 强调**只在非 hover 时生效**；hover 波整体覆盖它。
- 键盘 focus 与指针 hover 共用同一波（visualFocus 合并逻辑 `Hst`）；focusin/focusout 需单独监听（指针事件不因 focus 触发）。
- 失焦/移出必须清波（peak 归位），不留残留。
- 浮层 openDelay 120ms / closeDelay 80ms（Radix 参数）；浮层顶对齐刻度、右侧展开、320px。


## 实测达标：**该结论已被推翻并重写**（2026-10-27 第 24 轮）

### ⚠ 旧结论已删除（它错在指标口径）

原先这里记着「② 点击刻度滚动 438 帧 / avg 8.5ms / 掉帧 0」并据此宣布达标。**这条是错的，已删。**

**错在哪**：本页预算的主语是 **px/帧**（400~800px/帧、≤60ms/帧），不是 ms/帧。
而且「平均帧耗时」这个指标**会奖励长时间采样**：
438 帧 × 8.5ms ≈ 3.7 秒，远超一次动画最长 2.2 秒——采样窗口混进了大量动画结束后的空闲帧，
把 300ms 级的长帧摊薄成了 8.5ms 的均值。

**教训：量丝滑要用「px/帧 + 有位移帧的间隔」，不能用「平均帧耗时」。**

### TCP-01：长距离点击的真实表现（px/帧 口径）

采样条件：1280×820 / dpr2 / 45 刻度 / 深色 / 文档高 88752px / 视口 764px / Chromium 152。

| 采样（修复前） | 距离 | 有位移帧 | 平均 px/帧 | 最大 px/帧 | 最大帧间隔 |
|---|---|---|---|---|---|
| 点刻度[5] | 3369px | **2** | 1684 | **3362** | 1900ms |
| 点刻度[12] | 16468px | 61 | 270 | **3200** | 134ms |
| 点刻度[20] | 15029px | 48 | 313 | **2757** | 226ms |

**判定：最大 px/帧 2757~3362，是 800 预算的 3.4~4.2 倍；帧间隔最长达 1900ms。不丝滑。**

### 根因（有证据，非"疑似"）

1. 滚动期间 rAF 间隔被拉长到 **117~307ms**（不是掉一两帧，是每帧都慢）；
2. 同一时段只记录到 **1 个 longtask（204ms）** —— 所以**不是**长任务持续占满主线程；
3. **决定性对照**：只写一次 `scrollTop`、完全不排动画帧，最大帧间隔仍是 **116ms**，
   且只在宿主首次挂载新内容时出现 **1 次**。

→ **结论：宿主每挂载一批新内容要付 ~116ms 固定成本，这笔成本与插件是否做动画无关。**
动画帧之所以被拉长，是宿主在两次挂载之间占住了主线程、rAF 被推迟；
按时间算出的动画进度于是在下一帧一次跳过 1000~3000px。

### 已实施：瞬移到目标前 0.6 屏 + 尾段滑入

按本页第 29 行早就写好的方案实施（`turn-rail-zcode.ts` `animateScroll`）：

```ts
const dist = Math.abs(to - scroller.scrollTop)
if (dist > INSTANT_JUMP_MIN) {           // >1200px 才瞬移
  const tail = Math.max(SCROLL_MIN_MS * SCROLL_PX_PER_MS, scroller.clientHeight * SLIDE_TAIL_RATIO)
  scroller.scrollTop = to - Math.sign(to - scroller.scrollTop) * tail
}
```
跨数万像素的部分交给宿主**一次性挂载**（瞬移），只有最后 0.6 屏走动画——
动画帧只覆盖一小段距离，即使被推迟一两帧，单帧位移也远小于 800px。

### 修复后实测（第一版瞬移，已证明部分有效）

| 采样 | 总位移 | **瞬移帧** | 动画段帧数 | 动画段平均 | 动画段最大 | 动画段最大间隔 | 判定 |
|---|---|---|---|---|---|---|---|
| 刻度[5] | 2039px | 0（未触发瞬移） | 7 | 291px | **1015px** | 434ms | ❌ |
| 刻度[12] | 16802px | **1 帧 15777px** | 6 | 171px | **834px** | 166ms | ❌ |
| 刻度[20] | 14765px | **1 帧 13741px** | 6 | 171px | **861px** | 158ms | ❌ |

**瞬移策略本身是有效的**：15777px / 13741px 这部分的逐帧驱动被消除了，
动画段只剩 0.6 屏（约 458px），平均 px/帧 从 270~313 降到 **171**。

但仍未达标的两个原因，已定位：

#### 原因 1：瞬移那一步要 342ms，动画在它后面就撞车

逐帧追踪真实点击（刻度[12]）：
```
t=206970ms  dy=11443  dt=342ms   ← 瞬移（宿主同步挂载一大批内容）
t=207153ms  dy=3      dt=183ms   ← 主线程还没空出来
t=207295ms  dy=889    dt=142ms   ← 动画帧被这段挂载拖慢 → 单帧窜 889px
```

#### 决定性对照：动画代码本身完全达标

把同一个 458px 位移、同一条缓动曲线**单独跑**（不经宿主挂载竞争）：

| 时长 | 帧数 | 最大帧间隔 | 最大单帧位移 |
|---|---|---|---|
| 320ms | 15 | **28ms** | **122px** |
| 600ms | 28 | **34ms** | **78px** |
| 1200ms | 57 | **36ms** | **39px** |

**所以问题不在缓动、不在时长、不在插件动画循环** —— 是瞬移触发的宿主挂载与动画启动时序撞车。

#### 已修：双 rAF 让宿主挂载完成后再滑入

```ts
if (needsJump) {
  scroller.scrollTop = to - sign * tail      // 瞬移
  anim.frame = requestAnimationFrame(() => { // 第一帧：让浏览器提交挂载
    anim.frame = requestAnimationFrame(() => { slideTail(...) })  // 第二帧：主线程空出来后滑入
  })
  return
}
```

### 两条显式豁免（宿主动作，己方已定位到调用栈）

以下两条**不再写成「已达标」**。它们是宿主动作，插件无法缩短；己方已定位到具体调用栈，
视觉上不可感知，按豁免处理。

#### 豁免 1：瞬移与滑入之间 217ms 静止

| 项 | 值 |

| 现象 | 「跳一下 → 停 0.2 秒 → 滑 0.3 秒」 |
| 实测静止窗口 | 评审方 **217ms** ／ 我方 **342ms**（采样条件不同，机器负载也有影响） |

| 判定 | **豁免**——插件侧无可用 API 预挂载或分片挂载 |

#### 豁免 2：动画末尾 1 帧 100ms / 39~57px

| 项 | 值 |
|---|---|
| 现象 | 动画结束后约 100ms 出现 1 帧，位移 39~57px |
| 调用栈 | `at HTMLDivElement.set ← at ChatViewport.write (dsh-api-gateway/client.js)` |
| 成因 | 宿主 `ChatViewport` 的收尾校正写入 |
| 我方处置 | 已确认该帧**不是**插件动画（插件最后一帧是正常 16~17ms） |
| 判定 | **豁免**——这是判据「帧间隔 ≤60ms」的唯一破例；位移 <60px，视觉不可感知 |

### 剩下那 1 帧 100ms 是什么（已定位，不是插件动画）

逐帧日志显示插件的最后一帧是正常的：
```
t=162714ms dy=24 dt=16ms   ← 插件动画帧（正常）
t=162731ms dy=18 dt=17ms   ← 插件动画最后一帧（正常，已到位）
t=162831ms dy=39 dt=100ms  ← 100ms 后出现，位移 39px，无缓动特征
```

用 `Object.defineProperty` 拦截 `scrollTop` 的 setter 抓到调用栈：
```
at HTMLDivElement.set
at ChatViewport.write (dsh-app://app/plugins/??@deepseek-ai/dsh-api-gateway/client.js,...)
```

→ **这一帧是宿主 `ChatViewport` 的收尾校正写入，不是插件动画。**
插件无法控制宿主的写入时机；且该帧位移仅 39px，视觉上不可感知。
**这是宿主天花板，到此为止。**

### 互扰防护（本次修复中实测发现的一个真 bug）

第一版动画**没有**检查 scrollTop 是否被外部改动。实测：
```
宿主把视图拉到 67923（底部）
→ 插件仍继续写 8 帧
→ 最终停在 15555，离底部差 5 万像素   ❌
```

**修法**：每帧比对「当前 scrollTop」与「上一帧我们写入的值」，差超过 2px 即判定被别人接管，立即让位。

修复后：
```
插件写入 4 次 / 宿主写入 1 次 → 最终 68306 = 底部   ✅
```
**动画进行中来了新消息（跟随底部），视图不会被插件拽走。**

## 产物新鲜度守卫（2026-10-27 第 27 轮新增）

### 为什么必须有

评审方曾据一次「TCP-02 未修复」的复测下结论，**后来发现页面跑的是构建之前的旧 bundle**。
这类误判的代价是双向的：修好的被当成没修，没修的也可能被当成修好。

### 机制

- `scripts/sync-dist.mjs` 每次落盘同时写 **`lib/client.js.sha`**（sha256 + builtAt + bytes）；
- `scripts/verify-bundle-freshness.mjs` 进 gate，检查三件事：
  1. 部署目录 `client.js` 的实际 sha256 == `.sha` 记录值；
  2. 仓库 `lib/` 不比 `dist/` 旧（构建后没同步就红）；
  3. 非软链部署时，仓库 `lib/` 与部署目录逐字节一致。
- **反向验证**：篡改 `.sha` 里的哈希 → 红（打印「指纹记录 0000… / 实际计算 f691…」+ 修复命令）；恢复 → 绿。

**用法**：跑任何性能/交互验证前先 `node scripts/verify-bundle-freshness.mjs`。

## TCP-02：等待窗口内的外部写入（2026-10-27 第 26 轮评审指出，已修）

### 漏洞

互扰防护原先**只在动画开始之后**生效。`slideTail()` 是在滑入开始那一刻才取
`from = scroller.scrollTop`，而让位比对只写在 `step()` 里。
瞬移之后有**两个 rAF 的等待窗口**——宿主若在这段窗口写一次 `scrollTop`
（流式跟随底部每来一批内容就写一次），这次写入会被当成新起点，
插件接着**从底部往目标刻度滑**，用户看到的是"点了标签，视图自己往回拽一万多像素"。

**这不是构造场景**：用户最常点刻度的时刻就是「正在流式输出、想回看前面某一轮」。

### 修法

`animateScroll` 把瞬移后的位置存成 `jumpBase` 传给 `slideTail`；
`slideTail` **入口处**先比对一次：差 >2px 就 `scrollAnims.delete` 并直接 return。
让「等待窗口内的写入」与「动画中的写入」共用同一套让位逻辑。

### 判定表与结果

| 外部写入时刻 | 修复前距底 | 修复后距底 | 判定 |
|---|---|---|---|
| rAF 等待窗口内 | **18453px**（82 个向上拖拽帧） | **0px** | ✅ |
| 60ms | 0px | 0px | ✅ |
| 120ms | 0px | 0px | ✅ |

**回归测试**：`scripts/verify-scroll-yield.mjs`，已并入 `gate` 与 `test:layout`。
**正反向双验**：修复在位 → 绿；去掉入口比对 → 红（18453px / 82 帧）；恢复 → 绿。

## 2026-10-29 ZCode asar 二次校正（时长分档）

此前五档时长里若干值是推定，不是实测。这轮直接从 ZCode 安装包提取到原始声明：

| 场景 | ZCode 原文 | 我们此前 | 现在 |
|---|---|---|---|

| 分组折叠体 | `animation:.3s ease-in-out` | 300ms（与侧栏共用） | **300ms（独立 collapse 档）** |

### 操作行图标：一次自己造的溢出（2026-10-29，commit `c664479`）

统一按钮尺寸时把「整排所有按钮」都钉成 24px 硬宽 —— 但这一排里**混着两类按钮**：
纯图标（复制/重试/赞/踩/星标/删除/分享）和 **图标+文字**（带「记忆」二字的快照钮，内容宽 43px）。
24px 硬宽让文字挤到盒外，压住右边的删除钮。

**修法**：`width:auto; min-width:24px; padding:0 4px; white-space:nowrap`。
纯图标 = 14+8=22 → min-width 抬到 24（仍是 ZCode 的 24×24）；带文字按内容撑开。

**教训**：给「一整排」统一尺寸前，先枚举这一排里**有几种内容形态**。
纯图标按钮可以用固定尺寸，含文字的必须走 min-width + 内衬。
判据一行：`el.scrollWidth > el.getBoundingClientRect().width` 就是溢出。

**旁注（2026-10-29）**：这一排里 `重新生成 / 蒸馏本轮对话 / 此轮到后续全删除` 三个按钮带**内联样式**
（28×28 / radius 28px 胶囊，来自 dsh-session-kit 插件），内联优先级高于样式表，故仍是 28px 胶囊。
按仓库既有纪律（同 `dsh-po-btn`）**不覆盖其它插件的按钮**——它们不是宿主默认值，误改会越界。

### 图标「黑色粗细不一」的根因（2026-10-29，commit `afac4f5`）

用户截图里同一排图标有的纯黑、有的发灰。实测八个钮：

| 来源 | 钮 | color |
|---|---|---|
| 宿主 | 复制 / 好的回答 / 有问题的回答 / 在新对话中分支 | `rgb(38,38,38)` = 100% 前景 |
| dsh-session-kit（**内联样式**） | 重新生成 / 蒸馏本轮对话 / 此轮到后续全删除 | `rgba(38,38,38,0.5)` = 50% |

描边本身早已统一（全部 1.5px），差异只在颜色 —— 浅色下 100% 黑与 50% 灰的视觉重量差了近一倍，
读起来就是「粗细不一」。

**修法**：内联样式只能用感叹号优先级压过，新增一条、只作用于操作行按钮颜色
（`:is(.ppByMG_actions,.d1vkyW_actions) button`）。结构债记账 59 → 60。

**顺带发现的度量陷阱**：结构债计数器扫的是字面量 `!important`，**注释里写它也会被计数**。
我在注释里解释这条规则时写了三处，实测数字虚高到 63、门禁报「超出预算 4」。
**规则：解释 important 的注释不要写它的字面量，用「重要级覆盖」这类说法。**
