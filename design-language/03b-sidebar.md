## 2. 缺口清单（带判定表）

### G12（P1）· 会话行内边距模型与 ZCode 不一致

- **现象**：ZCode `padding: 4px 4px 4px 10px`、`gap: 8px`、内容右侧留白由 flex 撑开；
  DSH `padding: 0px 64px 0px 40px`、`gap: 0px`、靠大内边距给图标和时间让位。
- **影响**：DSH 行的可点区域形状与 ZCode 不同（左侧 40px 空白 vs 10px+图标），
  长标题可用宽度更窄（256−64−40=152px，ZCode 约 256−10−8−图标≈210px）。
- **判定表**：读列表行 `padding-left` 与可用文本宽度 ——
  `padding-left ≤ 12px` 且文本宽 ≥190px ⇒ 已对齐；`40px` ⇒ 未对齐。
- **风险**：中。DSH 的 40px 左内边距是给**树形缩进 + 图标**用的，
  直接砍到 10px 会让二级会话行与项目名错位。**必须先确认缩进由谁承担**再改。

### G13（P2）· 会话标题字重 400 vs ZCode 500

- **现象**：ZCode 会话标题 `font-weight: 500`，DSH `400`。
- **判定表**：读 `.dcu-wb-session` 内标题 span 的 `font-weight` —— `500` ⇒ 已对齐；`400` ⇒ 未对齐。
- **风险**：低。纯字重，且 DSH 用的字体在 14px 下 500 与 400 差异明显但不影响布局。

### G14（P1）· 分组标题色写死灰值（违反设计逻辑第 1 条）

- **现象**：ZCode 分组标题 = `oklab(0.87 0 0 / 0.6)`，即**前景色 60% alpha**；
  DSH `.dcu-wb-project-title` = `rgb(150, 150, 150)`，**写死的灰值**。
- **为什么这是真问题**：它违反 `01-design-tokens.md` 第 10 行
  「中性色永远以 alpha 叠加形式存在，不写死灰值」。
  实测令牌定义：`zcode-theme.ts` 里 `--dcu-sidebar-secondary` 深色 `#969696`、浅色 `#595959`，
  **两个主题各写死一个灰值**；而 DSH 自身已有对应语义令牌
  `--dsw-alias-label-secondary = rgba(212,212,212,0.6)`，正是 ZCode 的 60% α 手法。
  → 不是「没有正确令牌」，是**有却没用**。
  **修正我最初的判断**：我原本写「浅色下对比度只有 2.8:1、低于 AA」——**这条是错的**。
  实测 `#595959` on `#f0f0f0` = **6.15:1**，深色 `#969696` on `#161616` = **6.12:1**，两者都远超 AA。
  所以这不是可读性 bug，而是**令牌纪律问题**：写死值意味着将来主题或底色一变就失配，
  且它在语义上表达不出「次级前景」这一层。
- **判定表**：读 `.dcu-wb-project-title` 的 computed `color` ——
  含 `rgba(` 且 `alpha < 1` ⇒ 已修；`rgb(150,150,150)` 纯色 ⇒ 未修。
  同时读 `--dcu-sidebar-secondary` 令牌值：含 alpha ⇒ 已修；`#969696`/`#595959` ⇒ 未修。
- **风险**：低。改成一个令牌变量，视觉上深色几乎不变、浅色变清晰。

## 3. 本轮只修最上位 2~3 条的理由

- **G14 必修**：它违反已确立的设计逻辑（alpha 叠加），术语上叫「令牌纪律」。
  虽然**不是**我最初误判的可读性问题（对比度实测 6.15:1 / 6.12:1 双主题都达标），
  但 DSH 已有正确的 `--dsw-alias-label-secondary` 却没用，属于「有正确做法却绕开」，
  风险低（视觉几乎不变）、判定表明确，值得收口。
- **G13 可修**：纯字重，判定表明确，改一行。
- **G12 暂不动**：它涉及树形缩进模型，改错会让整个侧栏错位，
  需要先查清 40px 内边距里有多少是缩进、多少是图标占位——**盘点不足，不轻易动**。

## 6. 开合闪白缝（2026-10-28，commit `b425a5c`）

**症状**：深色主题下展开/收起侧栏时，侧栏与正文之间闪出一段白色。

**根因（两条叠加，都是"规则写了但没生效"）**：

| # | 问题 | 证据 |
|---|---|---|
| 1 | 兜底规则选择器写成 `html[data-dcu-codex-sidebar-initialized] [data-dcu-codex-sidebar-initialized]`，但该属性只打在 frame 上（`sidebar-width.ts` 的 `frame.setAttribute`），**html 上从来没有** | 实测 `document.querySelector('html[data-dcu-…] [data-dcu-…]')` = `false`；frame computed 恒为 `rgba(0,0,0,0)` |
| 2 | `--dcu-sidebar-background` 只定义在 `.dcu-root`（插件壳）里，而宿主侧栏列是它的**祖先** —— 祖先读不到后代作用域的变量，只能吃 `#f0f0f0` 浅色兜底 | 实测列 bg = `rgb(240,240,240)`（深色主题下） |

**为什么浅色皮肤下"看起来修好了"**：动画期露出的那 104px 一直透出桌面壁纸。浅色壁纸≈UI 底色，
不容易察觉；深色 UI + 浅色壁纸 = 白缝。**不是"浅色修好了深色没修"，而是这条规则从来就没生效过。**

**修法**：
- 选择器去掉 html 前缀，并**只在 `[data-dcu-sidebar-motion]` 期间**给 frame 上底色（动画结束即移除），
  静止态保留宿主壁纸/毛玻璃观感；
- `:root` / `body[data-ds-dark-theme]` 同步一份 `--dcu-sidebar-background`（浅 #f5f5f5 / 深 #161616），
  让祖先链能解析。

**验证（深色活体）**：收缩动画 7 帧 frameBg 恒为 `rgb(22,22,22)`；同期观测到 `gap=104px`
（正是修正前露壁纸的那段）；展开同样 7 帧同值；动画结束 `data-dcu-sidebar-motion` 已移除。
门禁 exit 0。

**教训**：写覆盖规则后必须验证「选择器真的匹配到了元素」（`querySelector` 返回非空 + computed 变化），
只看样式表里"存在这条规则"会漏掉这类假修复 —— 与 CODE-042（单规则探针假阳性）同族。

## 7. 收起跳步修复（2026-10-28，commit `c8b92b2`）

**现象（用户报告）**：收起侧栏时左下角「记忆/任务/归档」跳三下，顶部图标排跟着跳。

**逐帧定位**（rAF 采样页脚「记忆」项坐标，收起全程 79 帧）：

| 时间 | 事件 |
|---|---|
| t≈141ms | `cm-footer-stack` 在动画**第一帧**被 `display:none` → 文字行消失、剩余内容回流，记忆项当场下坠 108px（此时侧栏还是 264px 全宽、完全可见） |
| t≈150-460ms | 两壳交叉淡入淡出（本意的滑动动作） |
| t≈515ms | 宽度 264→56 落定 |
| t≈588ms | `dcu-compact` 落地 → 页脚再回流（248→40）、头部整体消失 —— 第二跳 |

**修法**：收起动画期间 `cm-footer-stack` 不再提前卸载（原地保留），
`.dcu-foot` 与 `.dcu-head` 整块随壳同步淡出（exit 档 120ms）；
紧凑内容等动画结束、宽度落定的同一帧出现 —— 内容切换被淡出盖住。

**复测**：整个收起过程页脚可见项位置变化 **1 次**（= 结束时的内容切换，发生在淡出完成后，不可见）；
修前是 2 次可见跳步 + 108px 坠落。展开/收起两态截图复核无异常。门禁 exit 0。

**回退**：`git reset --hard backup/pre-collapse-jump`。

### 7.1 二次修订：底部与顶部同步落位（commit `3ffd26e`）

用户复验：底部图标现在「慢慢浮现」，与顶部不同步。
原因：上一轮让页脚随壳淡出，但淡回用的是 move(300ms) 档，而紧凑轨图标是 enter(160ms)。

修订：
- 页脚 `transition:none` —— 内容切换与宽度落定同帧、瞬时完成；
- 收起动画期间页脚/头部保持可见、随裁剪滑走（撤掉整块淡出）；
- 紧凑内容在宽度落定帧瞬时换上。

实测：整个收起过程底部「记忆」图标位置变化 1 次（落定帧瞬时切换，透明度全程 1）；
180ms 中途帧与结束帧截图一致、已就位。
**结论（动效原则）：同一容器的成组内容切换不要用淡入衔接 —— 淡入时长只要和邻组不一致就会「分批出现」；瞬时切换 + 一次滑动才是「一步归位」。**

### 7.2 三段式时序的根治：点击即换（commit `e662960`）

用户再反馈：淡出方案仍不理想（底部比顶部慢一拍），且「滑完→停→内容跳」本身就是多余动作。

**根因**：`SIDEBAR_COLLAPSE_SETTLE_MS = 500` —— 内容切换被安排在滑动结束**之后** 500ms，
时序上必然是「滑过去 → 停一下 → 图标跳一下」。

**修法**：`SETTLE_MS = 0` —— 紧凑内容在点击帧就位，整个收起只剩「宽度滑到 56」一个动画；
expand 方向对称。收起动画期间页脚/头部保持可见的规则保留（§7），但因内容已提前切换，
实际不再有中间态可跳。

**断言同步**：`conversation-visuals` 的 SETTLE_MS 断言 500→0（理由改写）；
`client-runtime` 集成测试收起时序改为「冲刷 0ms 定时器 → dcu-compact 立即在位、
无 dcu-collapsing 中间态」，工作区树不重挂断言保留。

**实测**：连拍 80/180/300/450/700/900ms，80ms 帧与 900ms 帧完全一致
——紧凑轨从头到尾在位，无中间内容态。门禁 exit 0。

**方法论升级**：§7 的「卸载推迟到被遮住的时刻」只适用于「切换前后内容位置不变」的场景；
当切换前后是**两套不同布局**时，任何时序安排都会产生可见中间态 —— 正解是**把切换提前到
运动开始的那一帧**，让运动本身成为唯一的过渡。

### 7.3 入场动画回归（commit `13a85fc`，用户裁决）

用户复验：瞬时切换 =「直接闪现」，不好看。要求底部图标**像顶部一样**快速出现、有动画过程。

**修法**：紧凑轨恢复 `dcu-sidebar-compact-in` 入场（enter 档：淡入 + 左移 4px 归位），
页脚挂**同一支动画**（同曲线、同时长、同帧起跑）；展开方向页脚走 `dcu-sidebar-expanded-in` 对称。
reduced-motion 下由既有 §311 规则统一关闭。

**实测（getAnimations + 逐帧）**：收起后动画确认播放；顶部 0→0.71(183ms)→1(298ms)，
页脚 0.37(183ms)→0.89(243ms)→1(298ms) —— 同一窗口（≈190ms）内完成，上下同步。

**动效原则（终版）**：
- 内容切换发生在点击帧（SETTLE_MS=0，无中间态，§7.2）；
- 切换后的新内容用**一支共享的入场动画**快速归位（enter 档）——「快」由 enter 档保证，
  「同步」由同支动画保证，「自然」由位移+淡入保证；
- 淡入时长必须与相邻组**共用同一支动画**，而不是各自配时长（各自配必然分批）。

## 8. 侧栏透明度裁决（2026-10-29，OpenDesign 议题①，数据关闭）

**议题**：侧栏是否改半透明（透出 macOS vibrancy / 桌面壁纸）。
**数据**：OpenDesign V4 产出（`新UI区/layer3-compare.html`）——3 档透明度（60%/75%）×
3 种壁纸（深/中/浅）共 9 组合，WCAG 2.1 相对亮度实测（14px 正文门槛 4.5:1）：

- 半透明 60%：深壁纸下主标题 10.39、文件夹 5.21，但**分组标题 4.01 已破 AA**；
  中壁纸文件夹 3.41；浅壁纸主标题 3.25（侧栏整体"消失"在壁纸里）
- 半透明 75%：浅壁纸主标题回到 4.82，但文件夹 2.42、分组 1.86 —— 不可读
- 实色 #161616：**9 组合唯一全项 ≥4.5**

**关键差异**：ZCode 的半透明背后是**它自家设计的深色壁纸**（可控）；DSH 背后是用户
不受控的桌面壁纸（不可控）。ZCode 的半透明**不可迁移**。

**裁决**：**保持实色（#161616 / #f5f5f5），零代码改动。**
「深色外观 + 暗壁纸时启用 60-75% + `prefers-reduced-transparency` /
`prefers-contrast: more` 回退」作为可选增强挂账（需感知壁纸亮度，成本高收益低）。
